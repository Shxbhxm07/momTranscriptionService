The defects

D1

Speaker names are never resolved

Critical

llama-service/main.py:139 · api/core/mom.py

llama-service ships a /identify-speakers endpoint with a written and tuned SPEAKER_MAPPING_PROMPT that maps speaker labels to real names from self-introductions and direct address. The API never calls it. The only endpoint it uses is /summarize.

The consequence is not that names are missing — it is that the model has the names and cannot attach them to anyone. In the LEP minutes it wrote "Michelle raised a concern" in key_points and assigned an action item to "Rich", while attendees listed six anonymous tags.

Measured · LEP Committee Meeting, 17 min, 6 speakersgrep '/identify-speakers' api/ → 0 callers grep '/correct-transcript' api/ → 0 callers transcript names Rich, Allie, Michelle, Viv, Tori, Brit attendees bound 0 of 4 resolvable attendees field score 50% (count 6/6 correct, names 0%) action items w/ wrong owner 2 of 10

Fix

After label_transcript(), POST the labelled transcript to /identify-speakers, then rewrite the [Speaker_N] tags with any confidently-resolved names before calling /summarize. Keep the tag whenever the mapping is not corroborated.

Pros

  • The endpoint, prompt and parser already exist and are tested — no second prompt to maintain.
  • Targets the single largest measured gap; attendees goes from 50% toward 100%.
  • Named speakers make downstream attribution more reliable, so it partly fixes D3 for free — the model reasons better about "Rich said" than "[Speaker_1] said".

Cons

  • A wrong name is worse than no name. An anonymous tag is honest; a misbound name asserts a false fact about a real person in a document their colleagues read. This needs a confidence gate, not a best guess.
  • One extra model call per request (~15–40 s on this hardware).
  • The prompt was written for "Speaker A" style labels; it needs checking against the [Speaker_N] convention this API emits.
D2

Whisper translates English audio instead of transcribing it

High

api/core/engine.py:104 — "translate": "true", sent unconditionally

The translate switch is correct for Hindi and Hinglish, and the code documents why auto-detect matters. But it is sent for every file, including audio Whisper has already detected as English. The code comments call this "effectively a copy". I A/B tested it on your own audio, and it is not.

Measured · 3-minute slice, LEP meeting, detected lang = englishword-level similarity 90.2% (414 w vs 440 w) translate LOST: "CULP" "Harford" ← proper nouns "correct. Everything is" "mean when you" translate KEPT: "Allie" "Brandon" "LEP" ← capitalised transcribe KEPT: all of the above, but lowercased

Two proper nouns vanished entirely under translate. That is the README's noted "proper nouns degrade across the language switch", now quantified — and unrecoverable downstream, because the LLM cannot repair a word that was never written.

Fix

Detect the language on the first ~30 s, then pick the task: transcribe when the result is en, translate otherwise. The Hindi and Hinglish paths are untouched.

Pros

  • Recovers dropped words and proper nouns on English meetings — which is most of your current test set.
  • No risk to the multilingual path, which keeps today's exact behaviour.
  • Whisper's English transcribe path is its strongest and most-evaluated mode.

Cons

  • It fights D1. transcribe lowercases proper nouns ("rich", "culp"), and lowercase names are harder for the name-binding pass to spot. These two fixes must be tested together, not separately.
  • transcribe keeps every "um" and "uh" — harmless, since preprocessing strips them, but it lengthens the transcript.
  • Adds a branch and a second pass to a path that is currently simple and carefully documented.
D3

Speaker attribution uses segment overlap only

High

api/utils/formatting.py — _find_speaker()

Each Whisper segment is assigned to whichever NeMo speaker occupies the most of it. Whisper and NeMo run separate VADs, so their boundaries never line up — the code says so itself. When one Whisper segment straddles a speaker change, the whole segment goes to the majority speaker and the other speaker's words are silently reattributed.

Measured · symptoms in generated minutesLEP "Provide the Common Look licence" → owner = the RECIPIENT LEP "Touch base with Rich" → owner = Rich (the TARGET) GitLab one bullet emitted under BOTH Speaker_2 and Speaker_3 published research: segment-level speaker reassignment corrects >=40% of speaker-confusion word errors

Fix — three options, cheapest first

(a) Split a Whisper segment when a NeMo turn boundary falls inside it, rather than assigning the whole segment. (b) Enable word timestamps and assign per word. (c) Add a post-hoc reassignment pass over each segment.

Pros

  • (a) needs no new model and no extra inference — it is pure arithmetic on timestamps you already have.
  • Fixes the exact failure that puts a decision or an action item against the wrong person, which is the most damaging error class in minutes.
  • (b) is the approach WhisperX uses and is the strongest of the three.

Cons

  • (a) produces more, shorter turns — more [Speaker_N] tags, a longer transcript, and more tokens into an already tight budget.
  • (b) requires word timestamps from whisper.cpp and a rewrite of label_transcript(); it is the biggest change here.
  • None of the three helps if diarization itself clustered wrongly — this fixes alignment, not clustering.
D4

ASR garble is never repaired

High

llama-service/main.py:147 — /correct-transcript, zero callers

A second built-and-idle endpoint. TRANSCRIPT_CORRECTION_PROMPT exists to fix obvious ASR errors from context while preserving speaker labels, and it accepts a known_names list to anchor name correction. Nothing calls it, so garbled words travel all the way into the minutes.

Measured · garble that reached the finished minutes"the sick" → should be "SEC" (appears as "SICK team") "safety is saying" → garbled; became a person named "Safety" "Sweden sites" → should be "threat insights" "K-lead" → should be "QA lead" "challenge assessment" → should be "talent assessment"

Fix

Call /correct-transcript between labelling and summarising, passing any names resolved by D1 as known_names. The two fixes compound: confirmed names are exactly the anchor the corrector needs.

Pros

  • Repairs errors at the only point where they are still repairable — before the LLM builds facts on top of them.
  • Already written, already prompted; there is a term_corrector and a lexicon builder in the service to support it.
  • Directly removes the residue that the never-invent rules can only contain — the rules stop "Safety" becoming "Seth", but only correction removes "Safety".

Cons

  • It is a rewrite pass over the evidence. A correction model that over-reaches invents content in the one artefact everything else is scored against — the opposite of the property you want.
  • One more model call, and on a long transcript it is the expensive kind (large input, large output).
  • Needs its own guard-rail: the service already documents a case where an over-correction turned "coherent" into "Qdrant".
D5

Decisions and action items restate each other

Medium

llama-service/prompts.py — DECISIONS_EXTRACTION_PROMPT

The decisions prompt counts "a task directly assigned to someone by name" as a decision. The action-items prompt counts the same event as an action item. Both fills now always run, so the same fact reliably lands in both fields.

Measured · overlap between the two fieldsLEP 3 of 6 decisions restate an action item multispeaker 2 of 5 decisions restate an action item

Fix

After both fills, drop any decision whose text near-matches an action item's task — reusing the term-overlap helper already written for D6.

Pros

  • Deterministic, no model call, and reuses code already in the service.
  • Removes visible redundancy in the field readers scan first.

Cons

  • Some assignments genuinely are decisions — "Alan will serve as acting manager" belongs in both. A blunt rule loses that.
  • Inherits D6's threshold problem: the same overlap maths, the same inability to separate reworded duplicates from genuinely distinct items.
D6

Reworded duplicates survive the merge

Medium

llama-service/core/llm_manager.py — _is_near_duplicate()

The main pass and the focused pass both find the same task and word it differently. The current detector compares stemmed content words. I tested it against the real pairs, and bag-of-words cannot separate them: the duplicate sits below the threshold and a genuinely distinct pair sits just above it.

Measured · the actual pairs from the LEP minutesduplicate decision overlap 9/17 threshold 10.2 MISSED duplicate action item overlap 3/10 threshold 6.0 MISSED DISTINCT pair overlap 6/11 threshold 6.6 kept (correct) loosening enough to catch the first would merge the third

Fix

Compare meaning, not vocabulary — either a small local embedding model for cosine similarity, or one cheap LLM pass asked to merge duplicates in the finished lists.

Pros

  • Separates the two cases the current maths provably cannot.
  • An LLM dedup pass needs no new dependency — the model is already loaded and resident.

Cons

  • An embedding model means new weights, more unified memory, and a new failure mode on a box already at 99 GB.
  • An LLM pass adds latency and can itself merge two things that should stay apart — trading a deterministic error for a non-deterministic one.
  • Doing nothing is defensible. Both duplicated items are true; the cost is tidiness, not accuracy. The current strictness fails in the safe direction.
D7

The legacy fallback cannot produce structured fields

Medium

llama-service/core/llm_manager.py — _generate_mom_legacy() returns no content

When the JSON pipeline fails, the service falls back to a text pipeline that renders real minutes but returns no structured object. Today the API surfaces that document with a note instead of discarding it — but every structured field is still empty on that path, so a caller reading action_items gets nothing.

Measured · before the budget fix, LEP meetingJSON pass truncated mid-object -> invalid repair retry content=None (all budget spent reasoning) legacy pass 3,931 chars rendered, content = {} API response mom: null "no meeting content" <- false

Fix

Either parse the legacy render back into content, or delete the legacy path — its own comment already marks it TODO(Stage 6): Remove after JSON pipeline is production validated.

Pros

  • Deleting it removes an entire class of silent degradation, and a second copy of four large prompts that must be kept in sync with the JSON ones.
  • The raised token budgets have already made this path far less likely to trigger.

Cons

  • Deleting removes the safety net: a JSON failure would become a hard error rather than a degraded document.
  • Parsing the render is fragile — a text parser over LLM prose is exactly the kind of code that breaks quietly.
  • The legacy path is the only thing that has ever produced output when the JSON path failed. Retiring it needs evidence across more clips than we have.
D8

assigned_to equals assigned_by

Medium

llama-service/prompts.py — the rule exists and is ignored

The prompt says "NEVER put the same person in both". Five of the ten LEP action items are Speaker_1 / Speaker_1, and the multispeaker sample did the same for Rahul. The model is describing a self-commitment, which is real — but it fills the assigner slot with the owner rather than leaving it empty.

Fix

Clear assigned_by when it equals assigned_to, in the same post-parse step that already unpacks owner and deadline.

Pros

  • One deterministic line, no model call, no prompt change.
  • Enforces a rule the prompt already states, rather than asking the model again.

Cons

  • Loses a true fact — that the task was self-assigned rather than delegated. A dedicated flag would preserve it, at the cost of a schema change.
D9

Filler removal deletes legitimate repeated words

Medium

llama-service/utils/text_utils.py — _remove_fillers()

The rule \b(\w+)\s+\1\b collapses any doubled word. That is right for stutters and wrong for English that legitimately doubles.

Measured · run against the shipped function"he had had enough of the delays" -> "he had enough of the delays" tense changed "the fact that that happened is the issue" -> "the fact that happened is the issue" clause broken

Fix

Require three or more repeats for the generic rule, and keep a short allow-list for the handful of genuine English doublings (had had, that that).

Pros

  • Trivial change, immediately testable, no model involved.
  • Stops a preprocessing step from altering evidence before anything else sees it.

Cons

  • Real stutters are far more common in speech than legitimate doublings, so this trades a small semantic gain for slightly noisier input.
  • The measured damage is low — the LLM reads through "he had enough" without changing any conclusion.
D10

Two-character floor lets near-empty audio through

Medium

api/config.py:56 — MIN_TRANSCRIPT_CHARS = 80

Eighty characters is roughly one sentence. Anything above it goes to a full MoM run — a chunked pass, three extraction passes, and several minutes of GPU time — to produce minutes of a single utterance.

Fix

Raise the floor to a few hundred characters, and reject on a low distinct-word count rather than raw length, so a repeated hallucination loop is caught too.

Pros

  • Saves minutes of GPU time per junk upload on a machine where one request blocks the next.
  • A clear rejection is more useful to a caller than minutes of one sentence.

Cons

  • A genuinely short but valid meeting — a two-minute stand-up — would be refused. The floor has to be low enough to admit those.
  • Purely defensive: it improves nothing on the meetings you are actually testing.

What I would do, in order

D1 and D4 together, first. Both are already-built endpoints sitting idle, they reinforce each other — resolved names are the anchor the corrector wants — and between them they own the largest measured losses. Two HTTP calls in _audio_to_english(), no new prompts.

Then D2 and D3 as one experiment. They interact: transcribe keeps more words but lowercases the names D1 depends on. Testing them separately will give a misleading result on both.

D5, D8, D9 are an afternoon of deterministic post-processing with no model calls and no new failure modes. Cheap to do, cheap to revert.

D6 and D7 I would leave. D6's current setting fails in the safe direction and both duplicated items are true. D7's fallback has not fired since the token budgets were raised — retiring it needs more evidence than two meetings.
